Travlr Getaways: Building a Full-Stack Travel Experience

The project at a glance

Travlr Getaways brings together a customer-facing travel website, a database-backed trip catalog, and a separate administration interface. I built the original application with Node.js, Express, Handlebars, MongoDB, Mongoose, and Angular. I later created a static, responsive presentation so visitors could explore the design without installing a server or database.

The challenge was not simply to make a collection of attractive pages. It was to give travelers a clear way to explore destinations while providing an organized, authenticated workflow for maintaining the trip records behind those pages. The source demonstrates these capabilities; it does not include a complete original client brief, so this account avoids attributing undocumented requirements or business results to the project.

What I built and how the pieces work together

The Express application serves the public Home, Travel, Rooms, Meals, News, About, and Contact pages. I organized the page routes, controllers, and Handlebars templates under app-server, while app-api contains REST routes, controllers, authentication, and Mongoose models. That separation makes the distinction between rendering information for guests and managing application data explicit.

Trip information is stored in MongoDB. The customer-facing Travel controller reads trip records through the shared Mongoose model and passes them directly to its Handlebars view. I chose this direct model access for server-rendered pages instead of making the Express server send HTTP requests to its own API. The REST endpoints serve a different purpose: allowing the Angular administration interface to retrieve, create, and update trip records.

The API exposes public trip-list and trip-detail reads, plus authenticated creation and updates. The Angular interface uses a dedicated trip-data service for HTTP communication rather than duplicating request logic in each component. A small JSON seed dataset supports local setup and repeatable sample content.

Administrative workflows, state, and data integrity

I built Angular views for listing trips, signing in, adding a trip, and editing an existing one. Reactive forms track field values and validation; component flags such as submitted and isSubmitting control feedback and prevent repeated submissions while a request is in progress. Success and failure are handled through observable subscriptions, with navigation back to the listing after a successful write.

The selected trip code is saved in browser local storage when someone chooses Edit, then read by the edit view to load the record. The update request uses that original code to identify the existing trip, even if the editor changes the code field. Authentication tokens are also kept in local storage by the Angular authentication service, allowing authorized API requests after navigation or refresh. This is a practical demonstration approach, but browser storage increases the importance of preventing script injection and is a trade-off to revisit before production deployment.

On the server, Mongoose defines required trip fields, a unique trip code, a date, and a non-negative per-person price. The API accepts only explicitly permitted trip fields when writing records and runs schema validation during updates. This gives the interface immediate validation while keeping the database rules authoritative.

Authentication and security decisions

Passport handles credential verification, and user passwords are stored as salted PBKDF2 hashes rather than plain text. A successful login issues a time-limited JSON Web Token. Protected trip-write routes validate the token and look up the corresponding user before changing records; public trip browsing does not require a login.

Because a registered account can write trip records, public registration is disabled unless an operator explicitly enables it. The API also applies an in-memory limit to authentication requests, restricts the allowed administration origin, and sets browser security headers. These controls demonstrate defensive design, not a claim of production-ready role-based authorization: the implementation does not distinguish multiple administrative permission levels, and multi-instance deployments would need a shared rate-limit strategy.

Visual design and the later static presentation

I retained the resort site's recognizable coastal identity—sea-green accents, warm neutrals, destination imagery, and distinct panels for rooms, meals, and travel information—while improving the organization of the later static version. Shared header, navigation, footer, and travel-guide modules reduce repeated markup, and common CSS works alongside page-specific stylesheets so each section can retain its own character.

The layout aims to help visitors find essential information quickly: compare accommodations, preview dining, discover destinations, and read practical travel guidance. The static presentation also includes a dedicated case study, longer-form coastal articles, and informational pages. These pages are content and presentation features, not a substitute for the original application's data-backed workflows.

Accessibility and responsive behavior

The static website uses semantic headings and landmarks, descriptive link text, labeled forms, image alternatives where appropriate, skip navigation, and visible keyboard focus styles. Responsive CSS adapts content and navigation for narrower screens, while reduced-motion preferences are considered in the styling.

I approached accessibility as part of the interface structure rather than a decorative finishing step. Clear labels, predictable navigation, and readable content benefit keyboard users and visitors on smaller devices alike. These implementation choices are visible in the source, but they do not amount to a formal accessibility conformance certification or a claim that every browser and assistive technology has been tested.

Testing, limitations, and technical trade-offs

Source-level verification has included JavaScript syntax checks, CSS parsing, local-link and asset checks, seed-data validation, authentication regression checks, and tests of the static demonstration forms. These checks help catch broken references and predictable regressions; they cannot replace an Angular production build, live MongoDB integration testing, or a full browser-based accessibility and deployment review.

The most important trade-off is maintaining two clearly separated experiences. The original application demonstrates server-side rendering, persistent data, API design, and authenticated administration. The GitHub Pages version is intentionally static: its booking and contact forms validate inputs locally but do not submit reservations, send messages, process payments, or communicate with MongoDB. I chose that separation so a portfolio visitor can inspect the interface without being misled about what is live.

What this work demonstrates

Travlr Getaways demonstrates my ability to organize a multi-part web application, connect a browser interface to a REST API, model and validate persistent data, implement authentication, and translate a visual direction into a coherent customer experience. It also shows attention to maintainability: related responsibilities are grouped, repeated interface elements are shared, and the distinction between demonstration behavior and live functionality is documented.
